# Pattern rules: code-shaped patterns compiled to tree-sitter queries (roadmap wave 2, item 6)

`cpp/pattern.{hpp,cpp}`: `compile_pattern(grammar, text)` parses the pattern as a fragment with the
same grammar and turns its CST into one query; `pattern_matches` runs it. Surfaces: `lmok query
--pattern`, pack fields `pattern` / `capture` / `pattern-inside` / `pattern-not-inside`, and the lmcode
methods `ts.match_c` / `ts.match_python` (first slice: c and python only; json and bash patterns are
refused with exit 2 because their "code" has no expression layer worth a pattern language).

## Translation

- `$NAME` is substituted by the identifier `__lmok_mv_NAME` and `...` by `__lmok_ellipsis` before
  parsing, so the fragment parses with the ordinary grammar; the placeholders come back as leaf
  nodes and become `(_) @mv_NAME_k` (any one named node) and the argument wildcard.
- C fragments are parsed as a translation unit, then retried with a trailing `;`, then inside
  `void __lmok_wrap(void) {...}` (C forbids most statements and bare expressions at file scope);
  Python fragments are a module. The file wrapper and one `expression_statement` are unwrapped so
  the pattern names the construct itself (`strcpy($A, $B)` is a `call_expression`, matched inside
  any larger statement).
- Named children give structure. When any child has a field name the query uses `field: ...`
  (no anchors); otherwise the named-child sequence is anchored with `.` so it is exact
  (`{ return $V; }` has exactly one statement). Anonymous children appear only when they fill a
  named slot, in child order: `operator: "=="`, `operator: "->"`.
- Leaves (no named children) and string-like kinds (C `string_literal`, `char_literal`,
  `concatenated_string`, `system_lib_string`; Python `string`, `concatenated_string`) match by
  text: `(kind) @lit_k (#eq? @lit_k "text")`. A node with no named children at all, such as an
  empty `argument_list`, also matches by text, so `f()` does not match `f(1)`.
- Repeated metavariables add `(#eq? @mv_X_1 @mv_X_2)`; the first occurrence is the one
  `capture: "X"` reports. Comments inside the pattern are dropped.
- `...` removes the anchor on its side: `f($A, ...)` = first argument A, anything after; `f(...)` =
  any arguments. Outside an argument list it is an exit-2 error ("only supported as a call
  argument in this slice").

## Corner cases (checked, see tests/patterns/cases.json)

- Whitespace and formatting in the pattern are irrelevant (`strcpy ( $A ,$B )` compiles to the same
  query as `strcpy($A, $B)`); a target's formatting never matters either, it is a CST match.
- A comment in the TARGET between two anchored children breaks the anchor (`comment` extras are
  named nodes); patterns over argument lists with interleaved comments therefore miss. Documented,
  not worked around.
- A metavariable binds one named node. In a statement position (`if ($C) $S`) it binds the
  expression inside an `expression_statement`, not a block: write the block form explicitly.
- A metavariable in a C type position (`sizeof($T)`) parses as an expression operand, so it does not
  match `sizeof(int)` (a `type_descriptor`); use a literal type or `malloc($N)`-style shapes.
- `x++` and `++x` compile to the same query (both are `update_expression` with `operator` and
  `argument` fields; field queries do not fix order).
- ERROR/MISSING nodes in the pattern are an exit-2 error naming the fragment and the position
  (`pattern 'strcpy($A' does not parse as c (syntax error at 1:1)`); `a; b;` is "one statement or
  expression per pattern"; a comment-only pattern "is empty".
- Python's named/anonymous duplicate spellings (`lambda`, `await`, `yield`, `type`) do not affect
  patterns: a pattern always names concrete kinds.

Pinned by `tests/check-patterns.py` (22 cases + 5 error cases; the expected queries and matches were
generated by this compiler and hand-reviewed, the failing-first control is the pre-change binary that
rejects `--pattern` as a usage error) and run by `test.sh` on every native OS.
